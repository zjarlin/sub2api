# 账号榨干模式

管理员在「账号 → 编辑 → 榨干模式」启用开关，添加并排序 1～16 个文本模型。
可用拖动或上下移动按钮排序，并限制到账号已绑定的部分分组；不勾选分组表示所有已绑定分组。
关闭开关保留顺序，后续请求恢复普通调度。

例如某账号的顺序为 `glm-5.3 → qwen3.8-max → qwen3.8-flash`：

- `auto` 在现有 Responses / Chat Completions 入口先尝试该账号的 GLM，再尝试该账号的两个 Qwen，最后进入普通候选池。
- 账号有空闲并发且模型可用时持续优先选中，不参与普通池的负载、延迟与加权排序。
- 三个模型共用账号并发上限。抢槽发现已满，本次请求直接跳过该账号的后续模型，不排队等待；下一请求会重新检查。
- 明确指定模型时，只优先匹配该模型的榨干账号，沿用原有模型回退设置。
- 多个账号启用时，按现有账号 `priority` 从小到大、再按 ID 排序。
- 本次请求已失败的账号/模型组合不会在普通池重复尝试，同模型的其他账号仍可使用。

榨干顺序只作用于现有 Auto 策略中已经允许、能力匹配的候选。权限、渠道限制、上下文/工具/图片能力、账号总额度和禁用状态仍先检查。
原生 `previous_response_id` 与 guardian 父账号绑定优先；有不可移植历史的请求不会加入账号模型回退前缀。已经写出输出后不再换模型重放。

OpenAI 兼容 API Key 聚合账号的选定模型遇到普通 429 时，冷却记录按账号、基础地址、精确上游模型保存；其他模型继续可用。
凭据失效、钱包余额与明确的账号总配额错误仍由原保护规则处理。原生平台继续使用自身的专用限流规则。

## 配置与观测

复用管理员账号创建/更新 API 的 `extra.exhaustion_policy`，无需数据库迁移：

```json
{
  "exhaustion_policy": {
    "enabled": true,
    "models": ["glm-5.3", "qwen3.8-max", "qwen3.8-flash"],
    "group_ids": []
  }
}
```

模型必须已被账号的模型限制允许。若上游目录有 Qwen、账号显式映射却只有 GLM，应先补齐映射并验证上游可用，再启用顺序。
普通用户账号 API 不能授予或覆盖该策略；批量编辑不能批量写入榨干策略。
调度决策的 `layer` 为 `account_exhaustion`，Auto 候选观测包含 `account_id`、`reason` 与实际前缀顺序。

## 验证

- 后端：优先账号、满并发溢出、下一请求恢复、分组限制、原生续接绑定、模型独立冷却、Redis 错误处理；HTTP 覆盖 Responses / Chat Completions 的流式与非流式、同账号模型降级和普通池回退，以及 Messages 的明确模型请求。
- 前端：模型选项、排序、分组、开关保留、保存重载、无效配置阻止提交；相关 96 项测试、类型检查、i18n、生产构建通过。
- 基线对照：`TestOrdinaryFailureExhaustsCanonicalModelAccountsBeforeFallback` 的 5 个子用例在原始提交 `4e5462140` 与本改动中同样失败，涉及已有兼容性过滤与 advanced 调度。未将这些已有失败计为本功能通过。

部署与账号启用是独立操作。主工作区有其他会话的未提交改动时不得替换线上网关；源码交付不表示已为实际账号启用。
