# Auto 高可用设计

Auto 的可用性分三层：本实例能接入请求、能找到至少一个符合本次请求能力的账号模型组合、上游能在向客户端输出前完成推理。`/health` 只表示进程仍运行；`/ready` 检查 Auto 策略所在数据库和调度所需 Redis，供副本启动及发布切流使用。健康检查不会调用供应商，也不证明目录中的模型可推理。

## 请求内恢复

每次 Auto 请求在选路时固定候选计划。首选 `deepseek-v4.1-flash`，失败后先换同模型的其他可用账号；同模型不可用后按模型 ID 的同系列、相近版本顺序尝试其他符合输入、工具与协议能力的模型。候选只遍历一次，不递归生成链，不重复计费探测目录中的全部模型。

HTTP 429、上游瞬时错误、无正文成功包装、Chat Completions 流在首个语义输出前中断、无终态 EOF 等可恢复错误进入有界降级。账号模型的连续瞬时故障使用已有短期隔离；429 优先遵守有效的配额重置时间或 `Retry-After`，过期时间使用短冷却。已输出正文、推理或工具内容的流不能切换模型，否则会把两个不同推理过程拼成一个响应；这类请求必须返回明确的失败或中断终态。带 `previous_response_id` 等服务端状态的请求也不能安全换模型。

## 健康与观测

真实业务成功、失败会更新账号模型健康证据。定时付费探测只复查已有证据且到期的账号模型组合，最短间隔七天；未验证的目录 ID 不自动逐个首测。目录数量、模型别名和健康状态应分别展示，不能把“列出”当作“可用”。

Auto 请求返回 `X-Sub2API-Session-ID`、`X-Sub2API-Run-ID` 和 `X-Sub2API-Request-ID`，缺少客户端会话元数据时自动生成观测 ID。用同一 API Key 查询 `/v1/auto/routes?session_id=...&run_id=...` 可看到首选、实际完成模型、尝试顺序和终态。监控需分别统计完成率、上游 429、降级成功率、首输出延迟、`selected` 长时间未终结及 `interrupted`；仅统计有 Codex 元数据的请求会低估故障。

## 发布与故障域

新副本必须通过 `/ready` 和有真实正文、用量、账号 ID 的 Auto 请求验证后才切入。切流时保留旧副本，待旧 Nginx worker 和长流排空后退役，避免主动截断会话。发布验证既要覆盖 Responses 与 Chat Completions，也要覆盖流式和非流式，以及 429、断流、无正文与不兼容参数的模拟故障。

当前网关虽有两个应用副本，Nginx、PostgreSQL 与 Redis 仍部署在同一主机。整机故障、数据库不可用、所有供应商同时限流、客户端取消、已输出内容后上游断流和不可移植的服务端会话状态，无法由 Auto 内部降级消除。跨主机高可用还需要独立入口、数据库故障切换、Redis 冗余及各故障域的实际演练。Chat 桥接上游尚无跨响应头与正文的 Auto 首语义输出超时守护；极慢但不报错的上游仍可能占用请求，后续应增加停止于首语义输出的守护，避免中断正常长流。
